Is the from-scratch generator a full, faithful mirror of the AdCP bundle?

Read-only audit · emit/from-scratch working tree (/Users/konst/projects/acp-fresh) against v9.0.0-beta.4 · bundle 3.2, 1,054 portable documents

Comparison point: v9.0.0-beta.4, not main. main pins AdCP 3.1.1 and ships no schemas/cache/3.2 at all, so grading it against this population would charge it for documents that did not exist when it was generated. v9.0.0-beta.4 carries the bundle tree 47768de9f54f7ef87a514ccaf8390dfd9662e0d0 — byte-identical to the working tree's. Same 1,054 documents on both sides.

Across the v9 line the generated surface is near-constant: domains/ holds 1,088 modules at every one of integration/sdk-v9, beta.1–beta.4 and sdk/v9-prs-all4; its tree hash moves three times (cd317dfd for beta.1–2, a37118d1 for beta.3, 4a99dea3 for beta.4), so the choice among the v9 refs changes the fidelity reading but not the coverage one. main, for scale: 699 generated modules against a 664-document 3.1 bundle.

The answer, in one line: on refusals the two trees are equal where this audit could probe them (§B) — the from-scratch tree is not buying correctness the v9 generator lacks. What it is buying is a schema binding (§D) and a readable name per node (§C). What it is missing is breadth: 395 of 1,054 documents, and 12 of the bundle's 179 tool request/response documents — of which 161 of the 167 missing ones are blocked by a keyword a later row already covers, and 65 by just two leaf documents (§F).

One place theirs is ahead, and it is not a tie. Ours lowers format: uri to HttpUrl and so refuses 7 of 8 URIs the document accepts, where theirs' AnyUrl accepts all 8 (§E). strict_validate does not catch it: the narrowing is on the construction side, which the document check never reaches.

B · Fidelity, against the document

Neither tree was compared against the other. For each sampled document the document's own assertions are the expectation, and each tree is graded on whether its class enforces them.

One instrument here was wrong, and the wrong reading is instructive. Comparing each class's model_json_schema() keyword-for-keyword against the resolved document scored ours 12 defects against theirs' 26, with theirs apparently dropping minimum on integer properties in 6 of 23 documents. That comparison measures schema reporting, not enforcement. It is kept below for what it is, and the verdict is taken from the refusal probe instead.

Union exclusivity and closed objects

oneOf says exactly one branch matches, so a payload matching two branches is the one fixture that separates a faithful union from a widened one. Theirs renders these unions as a pydantic union whose JSON schema reports anyOf, which is what made this worth probing. No document in the fidelity sample states additionalProperties: false, so three that do were added.

The exclusivity question turns out to be unreachable on this population, and that is the finding. Of the 16 documents both trees cover whose root is a oneOf of two or more branches, 10 close every branch with additionalProperties: false, and the 6 that leave branches open (activation-key, data-provider-signal-selector, deployment, destination, signal-id, signal-pricing) all carry a discriminator. Searching every branch pair of all six found no payload matching more than one branch. So the merged payloads below are refused because they match zero branches — the label states the measured count — and oneOf versus anyOf is, on every union document both trees cover, a difference in the reported schema with no reachable difference in the accepted set. An earlier draft of this audit asserted that theirs' anyOf was harmless because the discriminator makes the branches disjoint; that explanation was wrong for bound-value, which has no discriminator and is saved by its closed branches instead.

E · The other direction: narrower than the document

§B asked "the document refuses it — does the class?", which catches a class that is too WIDE. The complement catches a class that is too NARROW: a payload the document ACCEPTS that the class refuses. A tree can be faithful on one and not the other, and this is where the two trees stop being equal.

266 document-valid payloads were generated across the 23 sampled documents and both trees accepted all 266. Hypothesis does not naturally produce a 2,000-character URL or an exotic URI scheme, though, so the format: uri case was built by hand.

Theirs is strictly more faithful than ours on format: uri, and this is the one place the audit found ours behind.
