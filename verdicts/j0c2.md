## THE ANSWER, in one line

**All 56 are `EITHER`, and it is ONE cause.** Every one of them is a bundle document whose
node states a **composition over OBJECT branches**. Upstream's generator cannot name a
composition as a class, so it names the branches `X1…Xn` and binds the document's word to a
type expression over them; we bind the document's word to a **base class the branches
extend**. Both are faithful readings of the same statement, and the proof that they are
readings of the SAME statement is that **the two sides' branches agree on the wire**:

| | |
|---|---|
| **(a) OUR DEFECT** — the document states a non-object and we emit a model | **0** |
| **(b) UPSTREAM'S ARTIFACT** — the document states an object and they flattened it | **0** |
| **(c) EITHER** — the document states a composition, both renderings legitimate | **56** |

So **no emitter change is owed**, and **a drop-in note is not the answer either**. What is
owed is a decision about the flat word's kind, and §"What decides it" below says what
decides it — measured on upstream's own suite, not argued.

## Why every row is a composition, read off the document

The node a declaration came from is `__adcp_schema__` — `codegen/emit.py`'s own `SchemaRef` —
and the bundle is the **patched** one (`codegen.patch.for_build`), the bundle a run reads. The
pointer is resolved at the node and never at the document root: resolving to the root would
call every branch of a root-level `oneOf` an object, which is the exact mis-reading this
partition exists to avoid.

**And the BRANCHES are read, not only the node.** A `oneOf` whose branches are SCALARS is not
an `EITHER` — a model is the wrong rendering of `{"type":"string"} | {"type":"number"}`
whatever the node's own keyword says, and such a row would be an `OURS` hiding inside a
composition. Each branch is resolved through one `$ref` hop to the node it names. Measured
over all 56:

| what the node states | rows |
|---|---|
| `oneOf` over object branches | 49 |
| `anyOf` over object branches | 5 |
| `allOf` resolving to a conjunction of object branches | 2 |
| **a branch that is NOT an object** | **0** |

**Zero scalar branches anywhere.** That is why (a) is empty, and it is a measurement rather
than the coarse rule's output.

The two `allOf` rows were the only candidates for (b) and they are not (b):

* **`core/vendor-pricing-option.json`** — `allOf` of [an inline object, `$ref
  core/signal-pricing.json`], the referenced document itself a choice. Upstream's
  `Annotated` is over 5 branches; our base has 5 children; **the five wire field sets are
  identical**, `applies_to_output_*`, `pricing_option_id` and `ext` included. Upstream loses
  nothing.
* **`core/package-signal-targeting.json`** — `type: object` with 3 own properties, conjoined
  with a 3-branch choice. Upstream's 3 branches and our 3 children both carry
  `activation_key`, `pricing_option_id` and `signal_agent_segment_id`. Again identical.

My first reading of these two was that upstream dropped the conjunct's own fields. **It does
not** — their generator expands the conjunction into the branch classes exactly as we do. The
hypothesis is recorded because it was wrong and the measurement is what settled it.

## What decides it — measured on upstream's own suite

`tests/` on this branch IS upstream's behavioural suite. All 791 files parsed with `ast` (a
name in a string or a comment is not a use), every use of one of the 56 names classified by
the operation. The denominator split is the repository's own declared record,
`survey/dropin/upstream-tests-about-their-generator.txt` — 104 files that grade THEIR
generator, 577 behavioural — so a site is attributed by that list and not by my judgement
about what a test is "really" asserting:

| how upstream's own suite uses these 56 names | sites | in the 577 behavioural | in the 104 generator |
|---|---|---|---|
| `TypeAdapter(X)` | 45 | 42 | 3 |
| `get_args(X)` | 4 | **0** | 4 |
| `X.model_validate` / `X.model_fields` / … (CLASS-shaped) | **0** | 0 | 0 |
| `isinstance(_, X)` / `issubclass` | **0** | 0 | 0 |
| `X(...)` direct construction | **0** | 0 | 0 |

**Upstream's behavioural suite uses these names in exactly one way: `TypeAdapter(X)`, 42
times across 15 files and 14 of the 56 names.** It never calls a class method on one, never
passes one to `isinstance`, and never constructs one.

And `TypeAdapter(X)` works on a base class:

| over the same 56 rows | |
|---|---|
| `TypeAdapter(X)` constructs | 56 of 56 |
| `TypeAdapter(X).core_schema` **is** `X.__pydantic_core_schema__` | 56 of 56 |
| `get_args(X)` answers a branch tuple | 0 of 56 |

Because pydantic takes the class's own core schema, `TypeAdapter(X).validate_python` **is**
`X.model_validate` — one code path, and the branch dispatch `tests_emit/test_union_dispatch.py`
grades is what runs. Demonstrated end to end on the name upstream validates most:

```python
TypeAdapter(ReportingControlTotal).validate_python(
    {"value_type": "integer", "name": "impressions", "value": "5", "unit": "impressions"}
)                                     # -> IntegerReportingControlTotal
ReportingControlTotal.model_validate(same)   # -> IntegerReportingControlTotal
```

**So the kind difference costs the behavioural suite nothing.** The only operation a base
class does not answer is `get_args(X)`, and all 4 sites that use it are in the 104 files
already outside the denominator — `tests/test_type_aliases.py` ("Get all types in the union")
and `tests/test_codegen_contract_compatibility.py`, whose own comment reads *"SignalRef is
`Annotated[SignalRef1 | SignalRef2 | SignalRef3, Field(...)]`; Pydantic lifts the metadata
into FieldInfo and keeps the union."* That is an assertion about upstream's generator output,
which is why that file is on the declared list.

**Which we should pick: keep the base class.** It is the strictly larger surface — it answers
every type-expression operation upstream's behavioural suite performs AND the class-shaped
operations an alias cannot (`model_validate`, `isinstance`, subclassing), and the payload
dispatch is the same object either way. Nothing in the behavioural set asks for `get_args`.
If a future row wants the loss closed without giving up the class, the derived form is a
module-level type-expression ALIAS beside the base — reading 10's "an alias is a NAME and
never a second type" — and that is an addition rather than a change of what the word means.

## ONE cause or 56

**One.** The cause is a property of upstream's generator and not of 56 documents:
`datamodel-code-generator` has no way to name a composition as a class, so for every document
whose node composes it emits the branches as numbered classes and binds the document's word to
a `typing.Annotated`/union expression over them. The evidence that it is one cause and not 56
coincidences:

* all 56 nodes state a composition — no row rests on a different document fact;
* 0 of 56 have a non-object branch — the rule does not have to decide a hard case anywhere;
* 50 of 56 have element-identical branch wire field sets, and the 6 that differ differ for
  four named reasons, each already a separate finding of this bead;
* the `Annotated`-versus-bare-union split inside the 56 tracks the document's own
  `discriminator` keyword 16 for 16.

The reverse direction is the same cause seen from the other side and is **4** names, reported
rather than folded in: `ContextObject`, `ExtensionObject` and `Tags` are `dict[str, Any]` /
`list[str]` on ours — the document's own free-form object and array, rendered faithfully — and
upstream wrapped each in a model. `SignalPricingOption` is ours re-pointing at
`core/vendor-pricing-option.json`'s root.

## What was NOT done, and what the instrument refuses

No emitter change, no `src/`, no `codegen/`, no `tests_emit/`. `./check` is untouched by this
row and was not expected to move: the only files added are `verdicts/j0c2.md` and
`survey/kind_differs.py`.

`survey/kind_differs.py` claims every set before reading a figure off it — the rule
`tests_emit/nodeset.py` states, *"a derivation that selects nothing passes every assertion
over it and is indistinguishable from a working check"* — and refuses with the set named when
one is empty. Three of them were empty during this row's own development and each refusal is
recorded at its site:

* the rows, when the record was read with `getattr` instead of `vars(cls)` — which attributed
  32 of upstream's hand-written subclasses to a document they did not come from;
* the branch sets, 56 of 56, when the base's pointer `#` was stripped before being used as a
  prefix for `#/oneOf/0`;
* the branch count, when `__subclasses__()` was taken for "the branches of this node" — ten
  of these bases also carry an `AdCPAsyncResponseData<X>` child declared at
  `core/adcp-async-response.json#/anyOf/<n>`, a branch of THAT document, which made ten rows
  look like a disagreement with upstream when the disagreement was with the instrument.

The third is the one worth keeping in mind for the next lane: **a base's subclasses are not
its branches**, because another document composing with it extends it too.
